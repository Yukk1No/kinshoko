# 数据与存储模型提案

2026-10-01。依据 [数据实践调查](../research/data-model-practices.md) 重新建模。多库、库内元数据、独立参考组、成员状态、合并与恢复的目标已确认；普通组保存引用、另提供带原图的包也已确认。下述身份规则、冲突处理和文件格式是本轮建议，尚未成为实现规格。

评审记录：[GitHub Issue #1](https://github.com/Yukk1No/kinshoko/issues/1)。

## 从现有实践取舍

| 调查依据 | 本提案的取舍 |
|---|---|
| Eagle 的素材可以属于多个文件夹，API 与磁盘 JSON 有差异 | 分类是元数据关系；导入保留来源身份与原始字段，兼容不要求采用 Eagle 的存储格式。 |
| ImoutoRebirth 分开记录身份、来源、路径；Curator 同路径换内容会复用 ID | 把图片身份、文件内容和存放位置分开，防止旧裁切指向另一张图。 |
| Hydrus 会保留被删除的标签；若只刷新来源标签，人工否决可能丢失 | 分开保存自动／导入结果和人工决定，人工否决也是需要保存的数据。 |
| BeeRef 的成员可以独立裁切，但嵌图会重新编码 | 成员拥有自己的显示状态；参考组包携带未经重编码的原文件。 |
| 部分图库的完整导出与合并实际保留不同字段 | 合并需要汇合元数据与建立引用映射；备份需要列明依赖并核验完整性。 |

以上是对调查的应用，具体证据与固定源码版本见 [Eagle](../research/eagle-storage-practices.md)、[图库](../research/library-storage-practices.md)、[参考板](../research/reference-board-practices.md) 与 [补充项目](../research/supplementary-data-practices.md)。

## 身份与归属

归属图见 [数据层级](data-hierarchy.md)。持久化至少分清以下四件事；它们不必各自成为一张表。

| 数据 | 建议身份 | 保存什么 |
|---|---|---|
| 资料库 | 稳定的 `library_id` | 库名、格式版本及库内数据；搬目录或改名保留 ID。 |
| 参考图记录 | 库内稳定的 `image_id`；跨库引用用 `(library_id, image_id)` | 一份原文件与该库对它的整理信息；同一原图可有多个导入来源。 |
| 原文件 | 完整文件的 SHA-256 与字节数 | 精确保留收到的文件字节，用于校验、判重与取回文件；哈希不代替图片记录身份。 |
| 存放位置 | 设备上的库目录，或存储后端中的文件位置 | 告诉应用去哪读数据；路径、盘符和远端地址可以变化。 |

建议原文件入库后不原地改写。换成不同字节的图片就建立新记录；外部程序擅自替换文件时报告校验失败，不让旧局部参考悄悄接管新内容。超分结果另外关联原图，模型与格式留在后续规格。

判重先计算完整哈希和大小，最终合并核验文件字节；局部哈希、缩略图、解码后像素或感知相似度只能用于找候选。建议一个库内相同原文件只保存一份，并汇合来源；跨库不依赖全局共享目录，保持每个本地库可独立搬走。

设备上的“未挂载／文件不可读”与用户执行删除分开记录。拔掉硬盘不会删除图片元数据，也不会作为删除动作同步到其他设备。

## 图片元数据

建议按用途保存，而不是把所有信息摊进一个标签数组：

- **属性与描述**：原文件名、格式、尺寸、方向、标题、来源 URL 与备注。标题和文件名各有用途，不相互覆盖。
- **整理关系**：库内标签、别名，以及为 Eagle 文件夹保留的分类与多重归属。分类目录不决定原文件在磁盘上的路径；同名分类不据名称直接合并。
- **来源记录**：来源资料库／导入来源 ID、外部 item ID、文件哈希及原始元数据。无法解释的 Eagle 字段先保留，导入报告说明哪些尚不可使用。
- **标签结果**：导入或模型给出的标签，连同来源、模型版本和该来源实际提供的置信度。重跑只刷新对应来源的结果。
- **人工决定**：对标签明确添加或否决；撤销人工决定才回到自动结果。否决与“当前没有这个标签”分别保存，重跑模型或重导 Eagle 都不抹掉它。
- **图上标注**：图片本身的区域备注归图片元数据；某个参考组成员的裁切只归该成员。

人工添加的标签参与筛选；人工否决的标签不参与；没有人工决定时使用当前有效的导入／模型结果。人工把“蓝发”改成“紫发”需要同时保存对前者的否决和对后者的添加。自动结果也是需要备份的数据，不能假定换个模型还能重建相同结果。

合并时，不同备注、来源和分类归属都保留出处。标签与别名按含义映射，名称相同但含义不兼容的项先保留为待处理冲突，不自动变成同一个标签。相反的人工决定也保留双方；**建议冲突未解决前，该标签不参与这张图的筛选，此项仍待确认**。

## 参考组、成员与携带原图的包

普通参考组是独立文档。建议保存 `group_id`、名称与成员列表，每个成员保存自己的 `member_id`、来源引用、裁切、画布位置／尺寸和视口缩放。来源引用包含 `(library_id, image_id)` 及预期原文件哈希，防止连接到内容已改变的文件。

同图在同组中用两次，就有两个成员。例如“眼睛组”的成员 A 裁眼睛、成员 B 裁头发，即使来源完全相同，也不能因图片去重删掉其中之一。参考视图是成员中的显示数据，无须另建可共享修改的持久化对象；建议单独保存一个视图时使用单成员参考组。

建议裁切使用完成方向校正后的原图像素坐标，布局使用参考组画布坐标，桌面窗口与屏幕 DPI 由显示层转换。增强图仍映射回原图坐标。Eagle 区域评论的坐标需样本核验后转换，暂不将未验证的区域评论直接当作裁切。

来源不可用时保留成员与布局，标明缺少什么。原图哈希相同的其他库可以提供重新连接候选；采用哪个库的图片记录及元数据，由用户明确选择。缓存预览不能冒充原图已恢复。

参考组包包含组文档、依赖清单和未经重编码的原文件；同一文件即使被引用多次也只携带一次。包内建立成员到文件的映射，使它能脱离原库打开；原库身份仍作为来源信息保留。包是否携带标签／备注等元数据尚未决定，也不等同于备份整个来源库。导入到新库时另生成来源到新记录的映射。

## 本地存储建议

建议采用 **每库一个 SQLite 元数据数据库＋普通原文件＋独立 JSON 参考组文档**。以下目录仅用于说明职责，文件名与公开格式尚未冻结。

```text
<用户选择的库目录>/
  library.json            # library_id、格式版本、元数据文件入口
  metadata.sqlite         # 图片记录、整理关系、人工决定、来源原始字段
  originals/ab/<hash>.png  # 原文件；库内路径相对库根目录
  derived/                # 预留需保留的超分结果，格式另定
  .cache/                 # 可重建的缩略图、搜索索引与渲染缓存

<用户选择的参考组目录>/
  <group-id>.json          # 成员、来源引用、裁切与布局
```

`library.json` 负责库身份与格式入口，SQLite 负责整理数据，避免同一字段在数据库和每图 JSON 中同时作为权威数据更新。应用自己的最近打开列表只记录位置，不成为图片、元数据或参考组的唯一存放处。

SQLite 适合事务更新与关系查询；代价是元数据需要数据库工具读取，不能靠逐文件文本合并解决同步。以后可提供可读的逻辑导出。采用 SQLite 不会让外部原文件和数据库自动成为同一事务。[SQLite 应用文件格式](https://www.sqlite.org/appfileformat.html)

建议入库顺序为：复制到临时文件并完成校验 → 放入原文件目录 → 提交元数据。中断可能留下无记录文件，重试与检查应能回收处理；不能把缺文件的记录报告为成功。参考组文档也需完整写入后替换，避免半份布局被当作已保存。

## Eagle 导入与库的变更

| 操作 | 建议规则 |
|---|---|
| 首次导入 Eagle | 为来源库分配 Kinshoko 的导入来源 ID，连同外部 item ID 保存；保留原文件、全部分类归属与原始字段，逐项报告成功、未支持和失败。 |
| 重导同一来源 | 用来源身份找到已有贡献；字节不变时刷新该来源元数据，保留人工决定；字节改变时新增图片记录，保留旧记录及出处。导入来源的路径可以更新。 |
| 多个 Eagle item 含相同原图 | 汇合到一个图片记录，保留全部来源 ID、备注和分类归属，不只保留先遇到的 item。 |
| 搬库或改名 | 保留库与图片 ID，更新设备上的位置记录；安全迁移需关闭写入或取得一致快照。 |
| 从列表移除 | 只移除设备上的打开登记，保留库文件；重新登记仍是同一个库。 |
| 删除资料库 | 先进入可恢复状态，永久删除另作明确操作；引用它的参考组保留成员并显示来源不可用，不自动改连别的库。 |
| 合并 A、B 为 C | 新建库 C；相同原文件汇成一条记录，其他文件各留一条，保留元数据来源和冲突；输出 A／B 图片、标签与分类到 C 的映射。 |
| 从备份恢复为独立库 | 分配新 `library_id`，保留库内记录关系并输出旧／新映射；之后可以主动合并。 |
| 持续同步同一库 | 各设备使用同一个逻辑 `library_id`，保持记录身份；传播整理变更与明确删除动作。具体协议尚未确定。 |

因为 A、B 仍然存在，合并后已有参考组默认继续引用原库；需要改连 C 时明确应用映射并核验原文件。恢复到独立库也按映射重新连接。直接复制目录会保留库 ID，注册副本时需区分同一库的迁移／同步副本与新建独立库。

## 备份、远端与同步的边界

库备份包含一致的元数据快照、快照引用的原文件和需要保留的派生结果；原始导入字段与人工决定随元数据进入备份，缓存可省略。独立参考组不因备份一个库而自动得到保护，需要单独选择或加入同一次备份任务。

若声明一份备份可以独立恢复选中的参考组，就必须包括它们的全部原文件依赖。建议先固定文档／数据库快照，保护本次所需文件不被清理，再复制并核验；所有依赖完整后才标记备份完成。SQLite 的备份 API 能取得数据库快照，外部文件仍需应用组织。[SQLite 备份 API](https://www.sqlite.org/backup.html)

远端接入需要分别支持取回原文件、存放备份，以及交换持续同步所需的变更。图片记录以文件哈希关联内容，具体本地／远端位置由存储接入解析；先保证完整本地工作副本，再验证按需取图。用户自有的免费存储可作为目标，具体服务未选定。

持续同步需处理同一记录的离线修改与删除，参考组是否纳入及如何解决冲突还要另定。各设备的本地 SQLite 是工作存储；不把正在写入的数据库文件交给网盘覆盖当作同步。WAL 模式依赖同机共享状态，迁移还要处理日志文件。[SQLite WAL 约束](https://www.sqlite.org/wal.html)

## 用具体场景检查模型

以下是待执行的验收场景，本轮只完成建模，未运行应用或真实库往返测试。

| 场景 | 应观察到的结果 |
|---|---|
| 同图的眼睛与头发分别加入组，再复制到另一组 | 每次使用都有独立成员状态，改动一处不会影响其他成员。 |
| 改盘符／库名后打开组；再拔掉源盘 | 位置更新后引用仍有效；不可用时保留组，不产生删除或偷偷换图。 |
| 在同路径换另一张同大小图 | 校验发现内容变化；旧裁切不自动指向新图。 |
| Eagle 一图多分类且含局部评论，重导前人工否决一个标签 | 分类与原始评论不丢，否决仍有效；坐标转换有明确核验结果。 |
| A、B 同图的人工标签相反，合并为 C | 一份原文件，双方元数据和冲突保留；旧组仍可用，改连 C 有映射。 |
| 跨库组打包后在空白设备打开；库与组一起备份再恢复 | 包恢复原文件与布局；备份另外恢复完整整理数据，并显式连接新库。 |

仍需确认：人工标签冲突的筛选行为、参考组包的元数据范围，以及备份交付范围。Eagle 导入样本与中断恢复验证通过后，再冻结存储格式；持续同步和超分各有独立规格。
