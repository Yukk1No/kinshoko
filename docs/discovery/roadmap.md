# Roadmap 方向

2026-10-06。本文记录已确认的能力方向；不是已排期的版本计划或实现规格。已排期的工作见 GitHub 里程碑（`v1.0` 是首个本地版本），没挂里程碑的 issue 是待办池；版本号与里程碑的约定见 [issue-tracker.md](../agents/issue-tracker.md#milestones-and-versions)。

| 方向 | 已确认的目标 | 尚未确定 |
|---|---|---|
| 本地绘画参考闭环 | Windows 单人本地；图片文件／文件夹、拖放、剪贴板与截图收集；自动标签参与检索，人工整理保留，多条件默认同时满足；Eagle 原图及组织信息迁入，重导保留人工整理，部分失败可重试；内容分级与全局安全模式；近似查找（内置近似对应表与个人近似对应表，#9 Q6）；验收按[验收约定](../validation/acceptance.md)；技术路线见[技术路线](technical-route.md) | 支持格式与标签模型的实测结果 |
| 多资料库管理 | 每库保存图片及元数据，可整体迁移；首版可建立、登记、切换多个库。资料库合并不进首版（#9 Q6），规则如下：合并保留来源并精确去重，冲突跳过后保持曝光，名称对应可纠正；移除与可恢复删除分开，恢复独立库；删图退出检索但既有组可用，永久删除提示影响并保留布局 | 名称规范化、删除恢复及其他验收规格 |
| 保存与复用参考组 | 独立跨库引用、成员状态独立；包携带所用原图及标签／备注／来源快照；同原图可临时补足显示而不改引用；合并后确认重连原组，恢复组为独立副本并连接恢复库 | 格式、来源校验与往返验证 |
| 清晰展示与桌面使用 | 首阶段静态图，动图保留原文件并静态预览；整图／局部以原图像素为基准，支持缩放；桌面选区固定，钉图置顶、可锁定，可贴边隐藏并交还焦点；截图钉住屏幕任意区域、钉剪贴板图片，截图历史可收藏进资料库（替代 Snipaste 的钉图用途）；钉图可翻转、旋转、调透明度 | 画师电脑上的钉图验收；右键菜单与贴边、缩放动画的设计 |
| 截图历史里的参考视图（待评估） | 不承诺做。截在参考图上时，截图历史现在存按原始像素裁下的 PNG（#227），收藏后资料库里多出一张原图的局部。可改为存参考视图：只记来源资料库、参考图、原图选区与方向，从截图历史钉住时还原成参考钉图，用“在 Kinshoko 中打开”代替收藏（#227 讨论，2026-10-21） | 要不要做取决于实际使用：收藏后库里多出原图局部是否成为问题，从截图历史再钉住时是否需要回到原图而不是一张固定的 PNG。做的话还要定截图历史的索引格式、来源失效或被遮蔽时条目怎样显示，以及交付阶段 |
| 收集与动态参考扩展 | 浏览器插件、网页批量采集、站点专用下载，动图播放／选帧及视频参考进入 roadmap；标注、取色、长截图等 Snipaste 的其他功能同样留在 roadmap | 支持来源、格式、检索和参考含义、性能与交付阶段 |
| 更多打标模型 | 首版只跑 PixAI Tagger v1.0；之后可接入 PixAI v0.9（输入 448²，显存需求预计明显低于 v1.0）与 WD SwinV2 v3（下载约 467 MB，也是 Q67 的显卡档后备）。换用另一个打标模型默认不重打已处理过的参考图，画师主动要求才重打；切换时让画师选择如何处理旧模型的结果，默认保留旧结果、新结果叠加。每个模型声明通过验证的硬件档，不支持的硬件加速选项置灰并注明原因，“自动”只在支持的档里选（#143 分诊，2026-10-18） | PixAI v0.9 没有内容分级输出：接入前须定分级来源（例如同时跑 WD）或未分级参考图在安全模式下的处理，不能让成人内容因未分级而显示；默认不重打与以图搜图特征指纹的关系：切换后沿用旧模型的完整特征索引，还是把特征补算作为切换的一部分（见[技术路线](technical-route.md)的 Tagging 预留）；各模型的固定版本、哈希、词表与阈值；验收机器上的显存、内存与 DirectML 正确性实测；手动选择精度是否放进“高级”；交付阶段 |
| 图片超分辨率 | 明确预留超分能力的研发工作 | 模型与部署、线条与颜色保真度、伪细节、性能、派生版本、局部坐标映射与交付阶段 |
| 备份与恢复 | 首个长期使用版本必须有经恢复验证的本地备份；默认全部已登记库与组，可按库缩小，执行前列清延伸依赖、范围、容量与未覆盖内容；库与恢复组为独立副本 | 远端备份阶段。首版本地备份的目标、频率与历史见[技术路线](technical-route.md#首版范围)（#9 Q7） |
| 人工纠正数据的自愿导出 | 用户可自愿导出人工标签纠正，供社区改进模型选型与标签映射；不做默认上传的遥测 | 导出格式、隐私范围与接收方式 |
| 安全模式的分级范围 | 设置中用滑条选择安全模式处理哪些分级；首版固定为 questionable 与 explicit（Q99） | 档位划分与交付阶段 |
| 按颜色找图 | Kinshoko 自己计算每张图的主色，可以按颜色找图。Eagle 的 `palettes` 导入时只原样保存、不解析，免得与新收图片的主色出自两套算法（#8 字段评审，2026-10-06） | 主色算法、颜色条件的表达方式、与基础检索的组合、交付阶段 |
| 智能文件夹 | 保存的检索在文件夹树中与普通文件夹并列，成员按条件实时计算；条件沿用基础检索（标签、文字、中文别名，默认同时满足，任一条件与排除由用户明确表达），并可按来源链接、所在文件夹、内容分级、导入时间等元数据筛选；例如画师 A 的智能文件夹自动收录作者为画师 A 的图。依赖基础检索与作者命名空间。Eagle 智能文件夹在上线时转换能对应的条件，不能对应的逐条报告，之前原样保存 | 单张图的手动排除或固定；作者从来源自动提取；交付阶段 |
| 以图搜图 | 从参考图、参考视图或截图出发，在满足全部查找条件的参考图内按相像程度排序；安全模式、内容分级与排除先生效，相像程度的门槛与计数也只在这些图内计算，被隐藏的图不以任何方式透露。条件栏中是独立、可删除的“像这张图”排序条件；它不改变结果集合，可调门槛只决定哪些图折叠为弱匹配，折叠后可展开，计数与分页按完整集合计算；没有其他条件时也可单独使用。不增减查找条件，不写入标签（与近似查找、语义搜索的区别见 [GLOSSARY](../../GLOSSARY.md)）。先用打标模型推理时产生的图像特征（[技术路线](technical-route.md)）；语义搜索落地后按实测决定是否改用其图片向量。截图与参考视图需要临时推理，走明确告知等待的慢查询交互（2026-10-16 讨论，依据 [本地向量检索调研](../research/local-embedding-search.md)） | 起点范围与慢查询交互的规格；打标特征在二次元参考上的效果；交付阶段 |
| 语义搜索 | 用一句描述找内容或氛围相像的参考图，排序、门槛与安全模式规则同以图搜图，可单独使用。模型以 EmbeddingGemma 2 为起点，按 Q67 先实测 ONNX Runtime + DirectML，不通过时再讨论是否重开 Q67。建索引在打标子进程内；查询时的文字编码在按需启动、闲置退出的查询子进程中（[ADR-0004](../adr/0004-tech-stack-and-process-model.md)）。模型是可选组件，首次使用时提示下载大小，精度取实测数值正确的最小者。向量索引是可重建缓存 | 中文与二次元题材的效果；fp16 数值问题；文字向量是否作为近似查找的来源（暂不决定，涉及 [ADR-0003](../adr/0003-tag-identity-and-approximate-search.md)）；与 Decisions 看图重排的组合及图片上传同意（随 [PR #75](https://github.com/Yukk1No/kinshoko/pull/75) 复核）；交付阶段 |
| 高级检索与辅助候选 | 基础功能之后逐步探索文字语法、正则等模式匹配与 LLM 辅助表达条件；命名空间前缀写法（`作者:某某`、`artist:某某`、`a:某某`）属于这里的语法。标签存时细、查时宽：近似查找把相近标签展开成可见、可改回精确的任一条件，内置近似对应表与个人近似对应表已进入首版（#9 Q6）；这里只保留另一来源：用户自填 API key 的 JEV 文字模型（远端，从当前库已有标签中选出该“或”的标签；不可用时退回内置近似对应表）。JEV 实测准确度达标后优先（[ADR-0003](../adr/0003-tag-identity-and-approximate-search.md)）。按图片内容排序的以图搜图与语义搜索各自成行，不属于近似查找 | 语法与适用字段、LLM 能力与接入、JEV 准确度、内置近似对应表首批四类之外的覆盖、上下位关系是否另做、性能与交付阶段 |
| HDR 显示与采集 | 原图永不改写，导入时记录色彩描述，派生图缓存键预留 `sdr`／`hdr` 变体；HDR 图片显示、HDR 桌面截图（FP16 采集）与 HDR 钉图（wgpu 的 scRGB 出口）进入 roadmap（#9 Q26，[ADR-0005](../adr/0005-two-path-display-pipeline.md)、[ADR-0014](../adr/0014-pin-colour-in-rust.md)） | WebView2 的 HDR canvas 可用性、HDR 格式范围、截图回显的恒等性、交付阶段 |
| 持续多设备同步 | 持续传递新增与修改，包含各设备编辑与离线使用；必须进入 roadmap | 设备范围、组文档范围、删除传播、冲突、同步时机与接入方式 |

一次性换机恢复属于备份与恢复。持续同步维护各设备上的同一个逻辑资料库。

基础检索先落实标签、文字和中文别名的同一组条件：多个条件默认同时满足，任一条件与排除由用户明确表达，返回整图候选。直接输入“某某”即可匹配，不需要写命名空间；同一个词命中多个命名空间或别名时，搜索框的候选下拉直接列出“作者：某某 ／ 角色：某某”供点选，不选就都匹配（Q96）。人物属性归属和区域识别另行验证；自由描述检索即上表的语义搜索。

建议后续依次探索更丰富的文字条件语法与模式匹配、模型辅助表达或检索候选。正则适用哪些字段、所谓“语法糖”如何表达，需另定规格；LLM 是候选方向，未承诺具体模型能力或选定接入方式；JEV 是远端文字模型，只用于近似查找。辅助条件让用户能看懂并修正，保留人工标签决定。

发起者提出优先免费方案或开放存储接口的方向。当前还未决定把哪些责任交给 Kinshoko，哪些配置或存储资源由用户提供。

本地备份与恢复是首个长期使用版本的交付门槛，需要用恢复后的原图、整理信息和参考组验证保护是否完整。向导默认保护本设备全部已登记库与组；按库缩小时一次算清关联组、完整外库和延伸依赖，执行前展示范围与容量，缩减后列清未覆盖内容。

存储接入的建议仍是用户选择目标，通过可替换接口使用本地目录或用户自有存储。该建议尚待确认，未选定具体工具或协议；同步流程的具体规格也未确定。

超分的数据关系建议是保留原图，把结果作为关联的派生版本。具体模型、元数据、显示选择与资源开销留在超分规格阶段，不在本轮选型。

资料库、元数据、参考组与存储位置的关系见 [数据层级与存储关系](data-hierarchy.md)。依据调查形成的身份、导入、合并与存储建议见 [数据与存储模型提案](data-storage-model.md)，尚未冻结格式或同步协议。
