# Roadmap 方向

2026-10-06。本文记录已确认的能力方向；不是已排期的版本计划或实现规格。

| 方向 | 已确认的目标 | 尚未确定 |
|---|---|---|
| 本地绘画参考闭环 | Windows 单人本地；图片文件／文件夹、拖放、剪贴板与截图收集；自动标签参与检索，人工整理保留，多条件默认同时满足；Eagle 原图及组织信息迁入，重导保留人工整理，部分失败可重试；内容分级与全局安全模式；近似查找（内置近似对应表与个人近似对应表，#9 Q6）；验收按[验收约定](../validation/acceptance.md)；技术路线见[技术路线](technical-route.md) | 支持格式与标签模型的实测结果 |
| 多资料库管理 | 每库保存图片及元数据，可整体迁移；首版可建立、登记、切换多个库。资料库合并不进首版（#9 Q6），规则如下：合并保留来源并精确去重，冲突跳过后保持曝光，名称对应可纠正；移除与可恢复删除分开，恢复独立库；删图退出检索但既有组可用，永久删除提示影响并保留布局 | 名称规范化、删除恢复及其他验收规格 |
| 保存与复用参考组 | 独立跨库引用、成员状态独立；包携带所用原图及标签／备注／来源快照；同原图可临时补足显示而不改引用；合并后确认重连原组，恢复组为独立副本并连接恢复库 | 格式、来源校验与往返验证 |
| 清晰展示与桌面使用 | 首阶段静态图，动图保留原文件并静态预览；整图／局部以原图像素为基准，支持缩放；桌面选区固定，钉图置顶、可锁定，可贴边隐藏并交还焦点；截图钉住屏幕任意区域、钉剪贴板图片，截图历史可收藏进资料库（替代 Snipaste 的钉图用途）；钉图可翻转、旋转、调透明度 | 画师电脑上的钉图验收；右键菜单与贴边、缩放动画的设计 |
| 收集与动态参考扩展 | 浏览器插件、网页批量采集、站点专用下载，动图播放／选帧及视频参考进入 roadmap；标注、取色、长截图等 Snipaste 的其他功能同样留在 roadmap | 支持来源、格式、检索和参考含义、性能与交付阶段 |
| 图片超分辨率 | 明确预留超分能力的研发工作 | 模型与部署、线条与颜色保真度、伪细节、性能、派生版本、局部坐标映射与交付阶段 |
| 备份与恢复 | 首个长期使用版本必须有经恢复验证的本地备份；默认全部已登记库与组，可按库缩小，执行前列清延伸依赖、范围、容量与未覆盖内容；库与恢复组为独立副本 | 远端备份阶段。首版本地备份的目标、频率与历史见[技术路线](technical-route.md#首版范围)（#9 Q7） |
| 人工纠正数据的自愿导出 | 用户可自愿导出人工标签纠正，供社区改进模型选型与标签映射；不做默认上传的遥测 | 导出格式、隐私范围与接收方式 |
| 安全模式的分级范围 | 设置中用滑条选择安全模式处理哪些分级；首版固定为 questionable 与 explicit（Q99） | 档位划分与交付阶段 |
| 按颜色找图 | Kinshoko 自己计算每张图的主色，可以按颜色找图。Eagle 的 `palettes` 导入时只原样保存、不解析，免得与新收图片的主色出自两套算法（#8 字段评审，2026-10-06） | 主色算法、颜色条件的表达方式、与基础检索的组合、交付阶段 |
| 智能文件夹 | 保存的检索在文件夹树中与普通文件夹并列，成员按条件实时计算；条件沿用基础检索（标签、文字、中文别名，默认同时满足，任一条件与排除由用户明确表达），并可按来源链接、所在文件夹、内容分级、导入时间等元数据筛选；例如画师 A 的智能文件夹自动收录作者为画师 A 的图。依赖基础检索与作者命名空间。Eagle 智能文件夹在上线时转换能对应的条件，不能对应的逐条报告，之前原样保存 | 单张图的手动排除或固定；作者从来源自动提取；交付阶段 |
| 高级检索与辅助候选 | 基础功能之后逐步探索文字语法、正则等模式匹配与 LLM 辅助表达条件；命名空间前缀写法（`作者:某某`、`artist:某某`、`a:某某`）属于这里的语法。标签存时细、查时宽：近似查找把相近标签展开成可见、可改回精确的任一条件，内置近似对应表与个人近似对应表已进入首版（#9 Q6）；这里只保留另一来源：用户自填 API key 的 JEV 文字模型（远端，从当前库已有标签中选出该“或”的标签；不可用时退回内置近似对应表）。JEV 实测准确度达标后优先（[ADR-0003](../adr/0003-tag-identity-and-approximate-search.md)） | 语法与适用字段、LLM 能力与接入、JEV 准确度、内置近似对应表首批四类之外的覆盖、上下位关系是否另做、性能与交付阶段 |
| HDR 显示与采集 | 原图永不改写，导入时记录色彩描述，派生图缓存键预留 `sdr`／`hdr` 变体；HDR 图片显示、HDR 桌面截图（FP16 采集）与钉图 WebGPU 渲染进入 roadmap（#9 Q26，[ADR-0005](../adr/0005-two-path-display-pipeline.md)） | WebView2 的 HDR canvas 与 WebGPU 可用性、HDR 格式范围、截图回显的恒等性、交付阶段 |
| 持续多设备同步 | 持续传递新增与修改，包含各设备编辑与离线使用；必须进入 roadmap | 设备范围、组文档范围、删除传播、冲突、同步时机与接入方式 |

一次性换机恢复属于备份与恢复。持续同步维护各设备上的同一个逻辑资料库。

基础检索先落实标签、文字和中文别名的同一组条件：多个条件默认同时满足，任一条件与排除由用户明确表达，返回整图候选。直接输入“某某”即可匹配，不需要写命名空间；同一个词命中多个命名空间或别名时，搜索框的候选下拉直接列出“作者：某某 ／ 角色：某某”供点选，不选就都匹配（Q96）。人物属性归属、自由描述检索和区域识别另行验证。

建议后续依次探索更丰富的文字条件语法与模式匹配、模型辅助表达或检索候选。正则适用哪些字段、所谓“语法糖”如何表达，需另定规格；LLM 是候选方向，未承诺具体模型能力或选定接入方式；JEV 是远端文字模型，只用于近似查找。辅助条件让用户能看懂并修正，保留人工标签决定。

发起者提出优先免费方案或开放存储接口的方向。当前还未决定把哪些责任交给 Kinshoko，哪些配置或存储资源由用户提供。

本地备份与恢复是首个长期使用版本的交付门槛，需要用恢复后的原图、整理信息和参考组验证保护是否完整。向导默认保护本设备全部已登记库与组；按库缩小时一次算清关联组、完整外库和延伸依赖，执行前展示范围与容量，缩减后列清未覆盖内容。

存储接入的建议仍是用户选择目标，通过可替换接口使用本地目录或用户自有存储。该建议尚待确认，未选定具体工具或协议；同步流程的具体规格也未确定。

超分的数据关系建议是保留原图，把结果作为关联的派生版本。具体模型、元数据、显示选择与资源开销留在超分规格阶段，不在本轮选型。

资料库、元数据、参考组与存储位置的关系见 [数据层级与存储关系](data-hierarchy.md)。依据调查形成的身份、导入、合并与存储建议见 [数据与存储模型提案](data-storage-model.md)，尚未冻结格式或同步协议。
