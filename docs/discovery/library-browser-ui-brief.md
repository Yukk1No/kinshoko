# 资料库浏览：前端设计简报与 demo 边界

2026-10-03。用户已确认图标侧栏、Axolotl Launcher 的动效参考，以及在 demo 中实现瀑布流。其余内容为本轮具体化建议；正式技术栈、交互细节和性能预算仍待验证。产品上下文见 [PRODUCT.md](../../PRODUCT.md)，功能提案见[首个正式功能](first-production-feature-plan.md)。

## 用户已给定的方向

- **任务与范围。** 面向边画边找参考的画师，界面围绕“打开资料库 → 浏览 → 看清整图与细节 → 回到原位置”组织。首个正式功能另包含建库、导入和重开；交互 demo 先验证浏览布局与操作，模拟导入／数据状态要明确标注，不能作为真实存取、画质或恢复证据。
- **图标导航。** 左侧用紧凑图标导航轨，名字通过悬停和键盘焦点提示，选中位置持续可见；按钮自身有可访问名称。当前资料库名称与切换入口应清楚。分类、筛选与元数据按任务出现，不把它们都堆进窄图标轨；详情信息区可收起，给图片腾出空间。
- **瀑布流必做。** 按图片比例分列，默认完整展示构图；不靠裁掉人物或局部来填满卡片。返回浏览时定位原图片与偏移，加载、切换结果、调整窗口宽度时保留稳定身份和明确排序。极端长图怎样限高并保持完整可查看，在 demo 中比较后决定。
- **Axolotl 动效。** 借鉴图标 hover／选中反馈、导航指示跟随及轻量展开／淡入。动画帮助理解状态；减少动画偏好要覆盖这些效果。图片区域保持不被透明、模糊或位移动画改变的观察基准。Axolotl 的参数是参考实现，不能直接当 Kinshoko 的性能结论。

以上参考来自 [Axolotl 固定源码核查](../research/axolotl-interface-reference.md)。目前尚未运行 Axolotl 或给 Kinshoko 选择完整视觉系统；通用图标、组件与材质在实际 demo 中按任务选择。

## demo 怎样给出答案

| 待验证问题 | 应完成的操作／证据 |
|---|---|
| 瀑布流是否节省空间且便于找图 | 同一批横／竖／方图对照等尺寸布局，记录留白与完整构图；按画师任务观察扫视和找到指定图片的过程，不能仅凭更密就判断更快 |
| 不同比例与内容是否可用 | 极端长图、宽图、透明图、小尺寸与细线图；中文长名称、无数据、加载中及单项失败状态 |
| 操作是否连续 | 选择图片、查看／缩放、返回原位置；改宽、快切结果、插入／移除、键盘移动与焦点仍对应同一图片 |
| 工作量是否受控 | 100／1,000／10,000 条构造记录；快速滚动、重复进入／返回；记录实际 DOM、耗时和内存，特别检查极端比例是否扩大虚拟范围 |
| 视觉反馈是否帮助操作 | hover、选中、信息区开合、加载完成；开关减少动画后重复同一任务，无独显与高 DPI 在桌面实验中确认 |

具体通过阈值留在[验收样本与指标](https://github.com/Yukk1No/kinshoko/issues/4)确认；构造记录只能验证界面工作量。demo 的素材应使用公开／自制图或经选择的小批真实图，保留来源与许可；不把自动生成标签当作已验证检索结果。

## 组件与工程边界

旧提案的 VirtuosoGrid 是等尺寸网格，不能直接承接这一要求。优先实验 TanStack React Virtual 的官方 lanes 布局，候选与缺口见[瀑布流依赖核查](../research/masonry-grid-reuse.md)。复用其分列、测量和虚拟化；项目承担图片卡片、选择／焦点、窗口改宽和按图片身份恢复位置的接入。

界面 demo 使用独立原型分支、内存状态及可复现启动入口；不写正式用户库。正式工程采纳验证结论、样本和经评审的合格代码，领域写入仍由 Rust 侧控制。浏览组件不拥有原图、元数据或参考组的存储权威。

待 demo 决定：图标的具体入口、信息区与原图查看的组合、图片密度／极端比例策略，以及宽度变化时的操作体验。配色、字体、阴影和精确动效值随实际视觉方向确定，不在本简报虚构一个已通过验收的设计系统。
