# 领域对齐记录

记录更新：2026-10-05。本文记录访谈中的共识与未决问题；当前尚未形成完整产品规格。

## 第一轮已确认

- **首个验收对象**：首位画师用户的 Windows 单人绘画工作流。
- **产品流程边界**：保存参考图 → 整理与检索 → 选择整图或局部 → 在绘画桌面使用。
- **最主要的痛点**：在自己的参考图库中找到需要的参考耗时最多，最妨碍绘画。
- **代表场景**：查找某种发色，或短发、长发、齐刘海、中分等发型；通过点击分类好的标签或输入文字找图，再截取需要的局部钉在桌面上。

以上首个验收对象用于验证阶段，未决定未来其他平台或使用群体的范围。

## 第二轮已确认

发起者明确接受 Q1～Q7 的推荐，并补充 Q8 的使用目标。

- **标签供给（Q4）**：自动提供标签建议，允许人工修正，并保留已有标签。
- **文字检索（Q5）**：首版让文字与点击标签表达同一组条件，支持中文别名与多个条件组合；自由描述检索另行验收。
- **局部参考（Q6）**：采用参考图加关联参考视图的概念；从同一张图选出眼睛和头发时形成两个视图，保留与来源参考图的关系。
- **Eagle 兼容（Q7）**：先把 Eagle 作为迁移来源，之后由 Kinshoko 独立管理图库；持续共用原库作为另一种接入需求。
- **存储与可靠性（Q8）**：本地使用是主要场景，素材备份与多设备同步必须进入 roadmap。发起者希望辛苦收集的素材在设备损坏后能恢复，换设备后仍可使用。具体规格尚未确定。
- **费用与扩展偏好（Q8）**：优先考虑免费方案或开放接口是发起者提出的方向；产品内置哪些流程、用户自行提供什么，仍需讨论。

## 第三轮反馈

- **Q9**：首个实用版本内置完整图库备份与恢复的提案，尚未得到单独、明确的确认。
- **持续同步（Q10）**：发起者指出换机恢复已被 Q9 覆盖；多设备同步必须表示设备间持续传递新增和修改，不能用一次性恢复代替。具体设备与同步规格仍在思考。
- **视图保存与参考组（Q11）**：发起者接受临时钉图与主动保存参考视图，并明确希望把多张图中的优秀局部组合起来，保存后整体复用。已记录“参考组”这一概念。保存成员关系已明确，是否保存摆放、尺寸与缩放仍待讨论（后由 Q13 确认）。
- **识别模型复用（Q12）**：发起者希望图片到语义标签的识别使用其他开源项目，并要求回看候选软件使用的模型。尚未确认首版检索对多人属性关联的承诺；需区分外部模型的输出能力与 Kinshoko 自己的检索含义。

## 第四轮已确认

- **多资料库（Q9）**：发起者以 Obsidian 的多库方式为参考，明确同一用户可以建立多个资料库，并对资料库进行合并、删除。“资料库”因此成为可独立管理的领域单位。各库的数据归属、合并方向、删除范围和恢复方式仍需明确。
- **持续同步的使用目标（Q10）**：按推荐，以各设备都能新增素材、修改整理信息并离线使用为 roadmap 目标。冲突处理、删除传播、后端与交付阶段未定。
- **检索结果的含义（Q12）**：按推荐，首版使用整图标签找到参考候选，不承诺多个属性属于图中的同一人物。自由描述、人物属性关联与区域识别仍需单独验证。
- **参考组复用（Q13）**：按推荐，保存成员关系及各视图的位置、大小、缩放，复用时恢复这些布局和显示状态。

Q9 原先涉及首个实用版本的备份保护范围。此次回答明确了多资料库模型；备份内置流程与具体交付阶段仍需在多库边界明确后落实，不据“不是覆盖”一词推定恢复或合并的操作方式。

## 第五轮已确认

- **资料库数据（Q14）**：发起者确认每个库应拥有图片 metadata；接受本地库的完整目录与整体迁移方向。资料库的正式定义扩展为参考图及其元数据。参考组的归属重新讨论，不能按先前提案归入某个库。
- **合并（Q15）**：接受生成新库 C、保留来源库 A、B 的推荐。完全相同的图片如何合并记录、metadata 冲突和参考关系迁移仍待明确。
- **移除与删除（Q16）**：接受从列表移除和删除资料库分为两个动作；移除保留文件，删除先进入可恢复状态，永久删除另作明确操作。
- **恢复（Q17）**：接受从备份恢复为独立资料库，之后可主动合并。
- **自动与人工整理（Q18）**：接受自动结果直接用于检索、人工决定优先，重新识别保留人工添加、修改与否决。
- **清晰展示与增强（Q19，2026-10-04 由 Q68 修订）**：接受以原图像素作为整图和局部参考的基准，支持缩放；1:1 不再作为要求；补充要求在 roadmap 中预留图片超分辨率工作。
- **模型表达**：发起者要求规划存储及数据关系的层级图。见 [数据层级草案](data-hierarchy.md)，图中未确认的归属和引用行为保留为提案。

## 第六轮已确认

- **参考组归属（Q20）**：参考组独立保存，可以引用多个资料库中的参考图。
- **成员状态（Q21，2026-10-04 由 Q71 补充翻转、旋转）**：每个参考组成员独立保存裁切、位置、尺寸和缩放，继续关联原图；在一个组中修改不影响其他组。
- **合并去重（Q22）**：合并后的 C 对完全相同的原图合并记录并汇合元数据，相似图和不同版本各自保留。

## 第七轮已确认与新提案

- **参考组携带方式（Q23）**：普通参考组保存来源引用、裁切与布局；另提供携带原图的参考组包，用于脱离原库使用或迁移。
- **重新建模**：依据工程实践提出 [数据与存储模型](data-storage-model.md)。图片身份与位置、元数据冲突、引用映射、具体格式和备份流程仍为建议，不据本次打包方式的确认推定其他提案已通过。
- **融合打磨**：按发起者要求融合 `85577e0` 与 `c07cb7c`，统一库身份由 SQLite 保存，补充文档版本、坐标与视口、撤销删除和备份范围；区分合并完整性与整理冲突。此项确认了融合工作，新操作细节仍为提案。

## 第八轮已确认

- **合并冲突（Q24）**：合并向导首先展示同一图、同一标签的相反人工决定，用户可以解决或跳过。跳过时保留双方出处及冲突标记，人工添加继续用于查找，增加后续发现与修正的机会。A 添加“蓝发”、B 否决“蓝发”时仍可用“蓝发”找到；双方分别添加“蓝发”“紫发”时两个标签都保留。普通无冲突的人工否决仍排除标签。
- **桌面局部参考（Q25）**：桌面钉图不修改选定局部的边界；移动与显示缩放不改变来源裁切。重新选择局部属于参考内容编辑流程，具体显示字段仍需原型验证。
- **备份的用户范围（Q26）**：用户按资料库理解备份，默认保护所选库及围绕它产生的参考内容（默认范围后由 Q43 更新为全部已登记库与组）；应用负责发现关联参考组和依赖，不向用户暴露组文件的单独备份颗粒度。参考组的独立归属不变。这一回答没有决定参考组包要携带哪些元数据。
- **备份向导（Q27）**：提供向导，引导选择需要备份的内容并说明覆盖范围。组引用外库时补选完整外库还是只携带依赖图片，仍在确认（后由 Q31 确认）。
- **合并后重连（Q28）**：先预览受影响组，经用户确认重连现有组到 C，并保存重连前备份；保留组身份，继续使用同一参考组。独立恢复后的重连规则不由这一确认推定。
- **检索条件（Q29）**：标签、文字与中文别名组合默认同时满足；任一条件与排除由用户明确表达。先满足基础功能，文字语法、正则等模式匹配、LLM 辅助表达条件与 JEV 提供辅助候选作为后续探索方向；具体语法、模型能力与接入方式待验证。
- **钉图状态（Q30，2026-10-04 由 Q68 修订）**：钉图位于绘画软件上层；锁定阻止移动、调整尺寸与显示缩放；鼠标穿透改为贴边隐藏，见第十二轮。状态不改变原图或裁切，交互与持久化细节留给原型。

## 第九轮已确认

2026-10-02，发起者接受 Q31～Q39 的全部推荐。

- **跨库备份（Q31）**：关联参考组引用外库时，向导默认提示补选完整外库；执行前列清追加范围与容量，由用户选择，接受体积可能增加的代价。
- **包的整理信息（Q32）**：默认携带所用图片的标签、备注与来源快照，不携带来源库的其他素材或完整操作历史；普通库备份仍保护完整整理数据。
- **来源失联（Q33）**：允许使用另一库的完全相同原图临时补足显示，不永久改写来源引用；永久改连需确认，完全缺失时保留成员、裁切与布局。
- **恢复组（Q34）**：备份恢复出的组是独立副本，连接恢复库。修复现有组则先预览、确认，再重连并保留原状态，与合并后继续使用原组区分。
- **标签与别名对应（Q35）**：同名标签默认对应，向导允许纠正；歧义别名保留两种含义，由用户明确查找条件，不静默合一。（2026-10-05 由 Q96 修订：歧义时在候选下拉中点选，不选则都匹配；两种含义仍不合一。）
- **Eagle 导入验收（Q36）**：原图、标签、完整文件夹关系、来源及整图备注作为实用版验收内容；区域评论保留原始信息，坐标核验后恢复显示；尚未支持的内容明确报告。
- **Eagle 重导（Q37）**：新增素材并更新 Eagle 提供的信息，保留本库人工整理；来源删图不自动删除本库副本，原文件内容变化保留新旧版本。
- **导入部分失败（Q38）**：保留成功项，整体标注部分成功；列出失败项和原因，允许重试，不重复创建已成功记录。
- **备份交付（Q39）**：允许正式存放、长期整理宝贵素材的首个实用版本，必须有经恢复验证的本地备份流程。远端备份、持续同步、超分和高级检索按 roadmap 推进。

## 第十轮已确认

2026-10-02，发起者接受 Q40～Q43 的全部推荐。

- **收集入口（Q40，2026-10-04 由 Q72 补充）**：首个实用版本支持图片文件、文件夹批量导入、拖放与剪贴板图片，以及截图收藏；浏览器插件、网页批量采集和站点专用下载进入 roadmap。
- **静态参考范围（Q41）**：首个实用版本以静态图片为验收对象；动图保留原文件，先提供静态预览，播放、选帧与视频参考进入 roadmap；暂不支持的格式明确报告。
- **图片删除（Q42）**：图片进入可恢复删除后退出普通检索，已有组仍使用保留的原图；永久删除前列出受影响组，之后保留成员与布局，缺失原图时明确提示。
- **默认备份范围（Q43）**：默认备份本设备全部已登记的库与组，也可按库缩小范围。向导在执行前一次算清关联组、完整外库和继续延伸的依赖，展示范围与容量后确认；缩减后明确未覆盖内容。

## 第十一轮已确认

2026-10-02～2026-10-04，围绕 [#4 验收样本与指标](https://github.com/Yukk1No/kinshoko/issues/4)。结果整理为 [验收约定](../validation/acceptance.md)。

- **样本来源（Q44）**：先用公开或自制素材与构造的 Eagle 样本，覆盖不足再补画师小批真实素材。
- **硬件分档（Q45，2026-10-04 修订）**：没有独显时允许体验降级；有 GPU 时使用 GPU，可采用更大的模型。首次自动打标可以较慢。
- **体验验收（Q46、Q49、Q51、Q53）**：没有测试用户群体，交互先按最佳实践做一版再迭代；首版不对找参考时间或体验做定量验收。画师找参考是筛选后浏览、看到合适的再选取，不以“找到一张图的耗时”作指标。客观门槛与画师定性反馈分开记录。
- **查询（Q46）**：约 12 条，约 8 条来自画师真实需求，另补单条件、组合、排除、中分与中文别名，分别标注来源。
- **样本存放（Q47、Q58）**：从 pixiv 等站点取图，仓库只提交含作品 ID、哈希、覆盖维度和来源元数据的清单，原图不入库。Eagle 样本在画师电脑上构造。
- **弱真值（Q48、Q54、Q62）**：不做人工标签标注。pixiv 作者标签与 R-18 标记作为弱真值；标签只出对照报告，分级设漏判门槛。画师对每条查询判断“这一屏值得刷吗”。
- **反馈渠道（Q55）**：原型提供默认关闭、只写本地的使用日志；社区通过 Issue 模板反馈；不做默认上传的遥测。人工纠正数据的自愿导出进入 roadmap。
- **硬件基线（Q50、Q56）**：以画师电脑为验收基线（AMD 独显、优动漫）；同机强制 CPU 作为降级档；开发机结果不作验收依据。
- **响应标准（Q57）**：采用通用交互响应标准，不与 Eagle 对比。
- **数据保护（Q52）**：导入、备份、恢复采用客观全通过；性能只记录。
- **钉图（Q59、Q63、Q64；验收项目 2026-10-04 由 Q73 修订）**：画师用绘王数位板与优动漫完成约 30 分钟绘画任务，WinTab 与 Windows Ink 两种模式分别通过；先依据参考板调查定交互方案，再做原型。其他设备组合进入社区兼容性矩阵，不作首版门槛。
- **内容分级（Q60、Q61）**：首版提供全局安全模式，覆盖浏览、搜索、参考组和钉图，模糊 questionable 与 explicit 并保留位置；新安装默认开启，可快捷切换。分级是自动建议，人工决定优先。样本含约 30 张 R-18 作品，由发起者下载。
- **模型选型（Q66）**：跟随社区默认 PixAI v0.9，WD SwinV2 v3 作后备；#6 只验证 PixAI 能否在验收机器上可接受地运行。（2026-10-04 修订：PixAI v1.0 已发布，默认改为 v1.0 FP16 社区 ONNX，本机改写为分块注意力；分级用 v1.0 自带输出，不另跑 WD；设置中允许切换模型并注明显存需求。见[验收约定](../validation/acceptance.md#选定结果2026-10-04)。）
- **GPU 路线（Q67）**：产品只走 ONNX Runtime + DirectML／Windows ML；ZLUDA 等 CUDA 兼容层不进产品。PixAI 认可的 ONNX 在 DirectML 上无法正确运行时，GPU 档先用 WD 官方 ONNX，PixAI 只在 CPU 档提供。
- **产出物（Q65）**：验收约定、样本清单格式、Issue 模板与本轮记录放入同一个 PR；#6 改写标题与问题，#3 记录体验迭代原则，#4 在 PR 合并后关闭。
- **按推荐接受的参数（假设值）**：样本 200～300 张，划出约 20% 为校准集，相同原图的裁切与近似重复不跨组；R-18 样本约 30 张，由下载者标注 questionable／explicit（2026-10-04 修订：发起者确认 R-18 真值直接以 pixiv R-18 标记为准，不分程度；首批 14 张已够用）；分级漏判召回率 ≥ 95%；操作反馈约 100 ms 内出现。Eagle 样本内容沿用 #8：一图多文件夹、标签、URL、备注、区域评论及两库相同原图。以上数值可由原型结果修正，修正前后两版都保留。

## 第十二轮已确认

2026-10-04，来自 [#7](https://github.com/Yukk1No/kinshoko/issues/7) 桌面钉图原型的两轮试用（[PR #21](https://github.com/Yukk1No/kinshoko/pull/21)）。Q68 是发起者与画师试用后的意见；Q69～Q73 由发起者按推荐方案确认（2026-10-04）。

- **穿透与 1:1（Q68）**：钉图不透明，本来就看不到下面的画布，鼠标穿透意义不大，改为贴边隐藏：一个全局键把全部钉图收到最近的屏幕边，并把焦点交还绘画软件，再按一次全部回到原位。1:1 没有需求，取消；整图与局部仍以原图像素为基准。
- **截图钉图（Q68，画师的意见）**：钉住选区改用截图的逻辑，不局限于已收藏的图，网上临时找到的参考也能直接钉，目标是替代 Snipaste。截图历史保留最近若干张并滚动删除，可以一键收藏进资料库；钉图上也提供收藏。钉图需要缩放、水平／垂直翻转、旋转 90° 与透明度等基本操作。剪贴板里的图片同样可以直接钉住，按截图对待。
- **库内局部（Q69）**：截图与选取库内局部使用同一个框选手势。框在 Kinshoko 中显示的参考图上时，得到按原图像素裁切、保留来源关系的参考视图；框在其他位置时得到截图。Q25（桌面钉图不修改选定局部的边界）继续成立。
- **参考组与截图（Q70）**：参考组只引用资料库中的参考图，[ADR-0002](../adr/0002-independent-reference-groups.md) 不变。保存参考组时列出尚未收藏的截图，由画师选择资料库后一并收藏。
- **翻转、旋转与透明度（Q71）**：翻转与旋转属于参考组成员，和裁切、缩放一样随组保存；透明度和置顶、锁定一样属于桌面使用状态。
- **首版范围（Q72）**：截图钉住、钉剪贴板图片、截图历史和收藏进入首个本地版本。标注、取色、长截图等 Snipaste 的其他功能，以及网页批量采集，留在 roadmap。
- **钉图验收（Q73）**：验收约定 #7 一节的穿透、退出穿透和 1:1 清晰度项目，改为贴边隐藏、交还焦点与截图保真，见[验收约定](../validation/acceptance.md#桌面钉图7)。
- **原型反馈**：可行性已证明；正式实现中，翻转、旋转等多数图片操作收进右键菜单等二级菜单；原型的贴边与缩放动画不合格，需要另行设计和验证。

## 第十三轮已确认

2026-10-04～2026-10-05，来自 [#8](https://github.com/Yukk1No/kinshoko/issues/8) 持久化原型（[PR #20](https://github.com/Yukk1No/kinshoko/pull/20)）暴露的规则缺口，以及由此延伸的智能文件夹与标签命名空间。除 Q86、Q95、Q96 按发起者的修正外，均按推荐确认。

**Eagle 导入**（原型试验后确认）

- **Eagle 回收站**：首次导入时，Eagle 回收站里的图进入本库的可恢复删除；之后 Eagle 再把图移入回收站，不改变本库状态。
- **来源搬家**：新位置与已登记来源的外部 ID 重合 ≥ 50% 时只作为候选，确认前不写任何数据；用户确认是同一来源则沿用登记、更新位置，确认是另一个来源则新登记，相同原图汇入已有记录。

**备注、来源链接与孤立文件**

- **整图备注（Q75、Q81）**：一份备注，规则同标签。画师没改过时显示来源备注并随重导刷新；改过以后以本库为准，重导不覆盖。清空也算改过；“恢复来源备注”撤销修改、重新跟随来源。同一原图有多份来源备注时都带上并注明出处，原始备注留在来源信息中。
- **来源链接（Q76）**：一个列表，每条注明出处，重导刷新对应的那条；画师可以另加或删除自己的链接，不修改导入的链接。
- **文字检索范围（Q82）**：只搜当前显示的备注与来源链接，不搜被覆盖的来源备注。
- **孤立原文件（Q77）**：导入中断后已写入库内、尚无记录的原文件，重试时复用；剩下的在“检查资料库”中列出数量与占用，用户确认后清理；备份不包含。

**文件夹**

- **文件夹的地位（Q74、Q83）**：文件夹是 Kinshoko 自己的组织方式，可新建、改名、移动，一张图可属于多个文件夹；Eagle 文件夹是迁入的初始内容。
- **图片归属（Q78）**：规则同标签，分来源归属与画师的添加／移出；画师的决定不因重导改变，没动过的归属随来源刷新。
- **文件夹本身的修改（Q79）**：画师改名、移动过的文件夹不再跟随来源；删除过的不因重导重新出现，也不把图放回。没动过的文件夹照常随来源刷新名称与层级。
- **来源删除文件夹（Q80）**：本库保留文件夹与归属，标记“来源已删除”，由画师自行删除。

**智能文件夹**（进入 [roadmap](roadmap.md)，Q89）

- **本质（Q84、Q85）**：保存的检索，成员按条件实时计算，在文件夹树中与普通文件夹并列；条件沿用基础检索，并可按元数据字段筛选。
- **Eagle 智能文件夹（Q87）**：功能上线时转换能对应的条件，不能对应的逐条报告；之前原样保存。
- **手动例外（Q88）**：单张图的排除或固定暂不决定。

**标签命名空间**

- **作者的表示（Q86，发起者修正）**：作者是一项元数据，按 E-Hentai 式带命名空间的特殊标签处理，可以点选、检索并作为智能文件夹条件。
- **命名空间与身份（Q90、Q91）**：命名空间是标签身份的一部分，`作者:某某` 与 `角色:某某` 是两个标签。“标签命名空间”与画师用于显示的“标签分组”分开命名，“分类”一词不再使用。
- **首批命名空间（Q92）**：作者、角色、作品，以及不带命名空间的一般标签；内容分级仍是独立概念。
- **作者的来源（Q93）**：只来自来源（如 Eagle 的 `artist:xxx` 标签、以后网页收集的 pixiv 作者）与人工，不用模型推断。模型给出的角色、作品进入对应命名空间，人工决定优先。
- **作者的显示（Q94）**：信息栏顶部单独显示，与来源链接并列，点名字可看该作者的全部图；存储与规则上仍是普通标签。

**检索**

- **直接输入（Q95，发起者修正）**：基础检索直接输入“某某”即可匹配，不需要写命名空间。前缀写法（`作者:某某`、`artist:某某`、`a:某某`）属于 roadmap 的高级检索语法。
- **歧义（Q96，发起者修正）**：同一个词命中多个命名空间时，搜索框的候选下拉直接列出“作者：某某 ／ 角色：某某”供点选，类似 Google 的补全；不选直接检索则都匹配。Q35 的歧义别名规则同步改为这一做法：两个标签照旧分开、不合一，只是从“先由用户选定再查”改为“候选中点选，或都匹配”。

## 基础领域总结

Kinshoko 服务画师收集、找到并使用绘画参考的流程，首个验收对象为 Windows 单人、本地使用。资料库拥有图片和整理信息，用户可管理多个库；参考组独立保存，可复用跨库整图或局部及其布局，普通组保存引用，携带使用时导出含原图与整理信息快照的包。

检索以整图标签候选为基础，支持标签、文字和中文别名，多条件默认同时满足；人工决定保留，未解决的合并冲突保持查找曝光。桌面钉图展示参考视图或截图，局部以固定选区展示，支持置顶、锁定和贴边隐藏；截图可收藏进资料库。

Eagle 是迁移来源，导入后独立管理；收集入口与静态范围、删除和恢复、合并与备份覆盖均已逐项确认。首个长期使用版本必须通过本地备份恢复验收。默认模型按 Q66 跟随社区并由 #6 实测确认，首版加入内容分级与安全模式；后续存储格式与各 roadmap 能力另定规格，整体总结供发起者核对。
