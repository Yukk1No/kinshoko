## 6. 实测数据

### 耗时（第 1 轮，按步骤与窗口大小）

从改完状态到 Present 返回（CPU），以及额外 `wait_idle` 量的 GPU 完成时间：

| 步骤 | 窗口像素 | 帧数 | 总耗时 中位／p95／最大 | GPU 完成 中位／最大 |
|---|---|---|---|---|
| 重画 | ≤ 0.5 MP | 110 | 0.51／0.84／8.3 ms | 0.02／0.21 ms |
| 重画 | 1～2 MP | 113 | 0.55／6.0／34.6 ms | 0.30／0.54 ms |
| 重画 | 2～3 MP | 16 | 0.52／10.1／18.3 ms | 0.37／0.54 ms |
| 重画 | ≥ 3 MP（铺满屏幕） | 267 | 0.46／10.8／25.4 ms | 0.45／0.68 ms |
| 换窗 | ≤ 0.5 MP | 9 | 9.0／10.9／10.9 ms | — |
| 换窗 | 1～2 MP | 11 | 9.9／11.1／11.1 ms | — |
| 换窗 | ≥ 3 MP | 4 | 8.2／10.2／10.2 ms | — |
| 挪窗（拖动） | ≤ 0.5 MP | 64 | 0.68／0.85／0.97 ms | — |

- 重画的 p95 和最大值来自 `Fifo` 的背压：交换链只排一帧（`desired_maximum_frame_latency = 1`），上一帧还没上屏时取下一个缓冲要等垂直同步，并不是在干活。GPU 实际工作 ≤ 0.7 ms。第 2 轮同样分布（重画铺满屏幕中位 0.52 ms）。
- 换窗的 8～11 ms 由三段组成：改交换链尺寸约 2.5 ms，Present 约 0.5 ms，`DwmFlush` 等合成约 3～6 ms。偶尔等合成到 30 ms（第 2 轮最大 37 ms），这时手势里这一格晚一到两帧上屏，但画面是对的。
- 每个阶段的换窗次数：一格一帧连续放大 90 格只换 5 次；每帧三格 5 次；隔 150 ms 慢滚 15 次（每格都是新手势：开始一次、停手一次）；拖动 0 次；动画 3 次；比屏幕大时 4 次；透明度 0 次。

### 背后最大化的 Edge 与全屏判定

| 场景 | Edge visibilityState | rAF／1 秒 | QUNS |
|---|---|---|---|
| 没有钉图 | visible | 171 | ACCEPTS_NOTIFICATIONS |
| 1 张钉图 | visible | 171 | ACCEPTS_NOTIFICATIONS |
| 8 张钉图 | visible | 171 | ACCEPTS_NOTIFICATIONS |
| 1 张放大到盖满屏幕（让出最下面一行） | visible | 171 | ACCEPTS_NOTIFICATIONS |
| 同上但不让出 | visible | 171 | **QUNS_BUSY** |
| 自测进行中（缩放、换窗） | visible | 171 | — |

不让出一行时 Edge 仍然 `visible`。可见 Chromium 的遮挡判定跳过这类窗口（工具窗口，或没有重定向位图），但全屏判定照样会报。ADR 0011 照用即可。

### 内存与显存（`marker.png`，24 MP，整张上传）

| 场景 | 进程私有内存 | 本进程显存（DXGI 查询） |
|---|---|---|
| 只建 GPU 设备 | 133 MB | 52 MB |
| 1 张 | 357 MB | 179 MB |
| 5 张 | 950 MB | 688 MB |
| 10 张 | 1 573 MB | 1 325 MB |
| 1 张放大到盖满屏幕 | 356 MB | 179 MB（交换链 +30 MB 显示期间） |

- 每张 24 MP 钉图约 125 MB 显存：RGBA8 纹理 96 MB 加 mip 32 MB。私有内存每张也涨约 120～150 MB，上传完 `wait_idle` 后不降，像是 D3D12 驱动或 wgpu 的上传堆留着没还。原因没查到，正式方案要再测一次。
- 盖满屏幕不比小钉图多花：交换链只有窗口那么大，纹理与窗口大小无关。
- **正式方案按显示尺寸上传派生图（第 5 节）**：屏幕上 1000×1500 的钉图约 12 MB 显存（fp16）。这一条是推断，没有实测。

## 7. 与 ULW 方案对比

| | ULW（前一个原型） | wgpu＋两槽（本原型） |
|---|---|---|
| 逐帧错位 | 0（约 1 900 帧） | 0（约 3 000 帧） |
| 铺满屏幕每帧 | CPU 约 12 ms，170 Hz 下掉到约 85 fps | CPU 约 0.5 ms＋GPU ≤ 0.7 ms，每个刷新周期一帧 |
| 改尺寸那一帧 | 和普通帧一样 | 8～11 ms（等合成），每次手势 1～2 次 |
| 常驻成本 | 无设备成本；每张图约 124 MB 内存 | 设备 133 MB 内存＋52 MB 显存；每张图按显示尺寸约十几 MB 显存（推断） |
| 颜色、HDR | 只能交 8 位 sRGB，HDR 走不通 | 输出 8 位或 scRGB fp16，HDR 有路 |
| 跨平台 | 只有 Windows | 渲染与几何共用，平台壳每个平台约几百行 |
| 画质 | CPU Lanczos3 精缩，停手帧与派生图逐像素相同 | 三线性 mip（手势与停手相同）；停手帧要与派生图一致时，可直接上传对应档位的派生图 1:1 显示 |

ULW 的一帧完整交出“几何＋像素”，这一点更省心，但像素必须在 CPU 上，所以大窗口慢、没有 HDR、绑死 Windows。两槽方案把原子性从“一次调用”挪到了“一次合成器提交”。这个机制在 macOS（CA 事务）和 Wayland（surface commit）上都有对应物。
