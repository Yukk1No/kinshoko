### 开发模式的含义

探针只在以下两种构建中存在：

- Vite 开发服务器（`npm run dev`）；
- 构建时显式设置 `VITE_KINSHOKO_PERF=1` 的生产构建（推荐用于测量：React 生产版，避开开发版的额外开销）。

条件在构建时折叠为常量。已在本容器核对：不设该变量的 `vite build` 产物中没有 `__kinshokoPerf` 与场景代码；设了以后单独出现一个 `install-*.js` 分块。

### 场景定义

| 名称 | 内容 | 驱动 |
|---|---|---|
| `wheel-steady` | 匀速滚轮：向下每秒 1000 像素，连续 10 秒 | 每个 rAF 按时间表写 `scrollTop` |
| `wheel-burst` | 快速连续滚动：每组 8 格（每格 100 像素、间隔 25 ms），组间停 175 ms，连续 10 秒 | 同上 |
| `ctrl-wheel-zoom` | Ctrl+滚轮连续缩放一次：光标在图片墙中央，放大 10 格再缩小 10 格，每格 50 ms，最后再记录 1.5 秒 | 先向图片墙派发合成的 Ctrl+滚轮；墙未处理（现状没有 Ctrl+滚轮缩放）时退回驱动图片大小滑条，步进相同（×1.1 取整到 10，140–420），结束时滑条回到原值。报告的 `driver` 字段如实记录用了哪一种。 |

已知限制：

- 写 `scrollTop` 是主线程滚动，量的是图片墙随滚动重新挂载、布局与绘制的帧时间；它不经过合成器的滚轮路径，也不量“从滚轮输入到画面首次响应”。这两项用真实滚轮加 `record(ms)` 与 WebView2 trace 另测（步骤 5）。
- 滚动场景每 250 ms 采样一次视口内缺缩略图的比例（`thumbnails` 字段），采样会读一次布局。要最干净的 trace 时传 `{ sampleThumbnails: false }`。
- 合成的滚轮事件不是可信输入，不会触发 WebView 的页面缩放。

### 报告格式

`run()` 返回 JSON：`environment`（UA、DPR、屏幕与视口尺寸、校准出的刷新间隔与 Hz、当前范围张数、图片大小）、`budget`（合格线）、`scenarios[]`（每项含 `driver`、`durationMs`、`scrolledPx`、`frames`、`thumbnails`）与 `warnings`（例如当前范围不足 5000 张）。

`frames` 字段：

- `p50`／`p95`／`p99`／`max`：帧间隔（毫秒）；
- `droppedFrames`／`dropRate`：按校准出的显示器刷新间隔，一帧跨了 n 个刷新间隔算掉 n − 1 帧；
- `droppedFrames60`／`dropRate60`：按 60 Hz 帧预算计的掉帧，合格线（≤ 1%）用这一项；
- `longTasks[]`：`kind`（`longtask` 或 `long-animation-frame`）、相对开始时刻、时长，LoAF 另带 `renderDuration`、`blockingDuration` 与前 5 个脚本来源；
- `pass`：p95 ≤ 16.7 ms、p99 ≤ 25 ms、掉帧 ≤ 1% 三项与总判定；
- `atRefresh`：显示器刷新率下的 p95 预算与结果（170 Hz 为 5.9 ms），只记录不卡口。

#102 对“掉帧 ≤ 1%”没有写明按哪个刷新率计；本单按 60 Hz 帧预算判定（与 p95 ≤ 16.7 ms 一致），170 Hz 的掉帧率同时记录。若负责人要按 170 Hz 卡口，在 T8 前定下。

## 测量步骤（负责人开发机）

设备：2560 × 1440 @ 170 Hz，RTX 4070 SUPER，Ryzen 7 5800X，Windows（版本待记录）。

1. 生成样本（约 1 分钟、约 60 MB）：
   `node scripts/perf/wall-fixture.mjs <样本目录>`
2. 构建测量版（PowerShell）：
   `$env:VITE_KINSHOKO_PERF = "1"; npm run tauri build -- --debug --no-bundle`
   记录提交 SHA 与 `target/debug/kinshoko.exe` 的 SHA-256。用独立的 `KINSHOKO_DATA_DIR`，不碰正式配置。
3. 新建图库“帧时间基线”，用“导入 ▸ 整个文件夹”导入样本目录，等导入与缩略图生成结束。窗口最大化，图片大小保持默认（240），侧栏选该图库的“全部图片”，安全模式关闭。
4. 在主窗口打开 DevTools（右键 ▸ 检查），控制台运行三次，每次另存：
   ```js
   r = await __kinshokoPerf.run(); copy(JSON.stringify(r, null, 2))
   ```
   存到 `docs/implementation/evidence/spec102-t07/baseline-run{1,2,3}.json`。三次间不改窗口、不改密度。核对 `warnings` 为空、`environment.refreshHz` 约为 170、`environment.total` 为 5000。
5. WebView2 performance trace：DevTools ▸ Performance，开启 Screenshots 与 Web Vitals，点录制，在控制台运行
   `await __kinshokoPerf.run({ sampleThumbnails: false })`，结束后停止录制，导出 trace 为 `evidence/spec102-t07/baseline-trace.json.gz`。另录一次真实滚轮：录制中运行 `r = await __kinshokoPerf.record(10000)` 并用鼠标滚轮快速连续滚动 10 秒，存 `baseline-real-wheel.json` 与对应 trace。
6. 提交前检查隐私：trace 与报告中若出现本机用户目录，按 `docs/implementation/evidence/REDACTION.md` 的做法替换为 `%USERPROFILE%`；截图只截应用窗口。

## 瓶颈分析（待测，TODO）

> TODO：以 trace 与 LoAF 归因为准写结论。

下面是**读代码得出、尚未测量的假设**，只用于决定 trace 里先看哪里，不能当作结论：

1. 每个 scroll 事件都 `setViewport`，整个 `Wall` 重新渲染，所有挂载的卡片重新生成 React 元素（`src/wall/Wall.tsx` 的 `onScroll`）。看 trace 中 scroll 事件后的 React 提交耗时。
2. 同一处理里每个 scroll 事件都 `captureAnchor` 并同步写一次 `localStorage`（`saveAnchor`）。看 `onScroll` 的自身耗时。
3. `mounted` 计算里对每个可见序号做 `found.includes`，对锚点与动画做 `ids.indexOf`；卡片多时是 O(n·m)。
4. 卡片以 id 为 key 按视口进出挂载与卸载，每次新建 `<img>`，缩略图经 `thumb` 协议取回再解码；`decoding="async"` 已有，但没有按滚动方向预取。看 Decode Image 与网络（自定义协议）条目、视口缺缩略图比例。
5. 读下一页（每页 500 张）后的布局效果对所有卡片 `getBoundingClientRect` 并逐个启动 Web Animations（`measureBeforeReflow` 与重排动画），可能在页边界形成长任务。看长任务的开始时刻是否与 `scrolledPx` 中的页边界对得上。
6. 缩放（滑条代驱）每格都 `measureBeforeReflow` 并对视口内所有卡片做 FLIP 动画，220 ms 后按新尺寸重新浏览全部已读页面。
