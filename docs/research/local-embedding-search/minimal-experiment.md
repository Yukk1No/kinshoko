# 8. 最小实验计划（未执行）

样本使用现有清单：[`sample-manifest.pixiv.json`](../../validation/sample-manifest.pixiv.json) 共 238 张（evaluation 185 张，calibration 53 张），覆盖维度包括 `hair:*`、`style:twintails／ponytail`、`bangs:blunt／hime／middle-part`、`length:*`、`lineart`、`grayscale`、`thick-paint`、`backlight`、`multi-person`、`full-body`、`very-tall` 等；[`sample-manifest.pixiv-r18.json`](../../validation/sample-manifest.pixiv-r18.json) 共 14 张。覆盖维度和作者标签都只是弱真值（[验收约定](../../validation/acceptance.md)）。

1. **文字找图。** 从覆盖维度生成查询，每个维度分别写中文、日文和英文版本，例如“双马尾”“ツインテール”“twintails”“逆光”“黑白线稿”；所有带该维度的 evaluation 样本都视为期望结果。仿照 DigUp `evals` 的格式记为 `{q, expect, tag}`。文字查询一律加模型卡建议的查询前缀，另做一组不加前缀的对照，单独报告差异。**这一组只衡量“像标签的概念”能否跨语言找到，不能代表语义搜索。** 另需一组由画师写的复合描述，例如“逆光下的侧脸”“低头整理头发的背影”“冷色调的雨夜氛围”，每条对候选图逐张做独立的分级相关性判断（相关、部分相关、不相关）；是否保留模型以这一组为准。比较四种做法：(a) PixAI 标签＋翻译表的精确条件；(b) 只用 EmbeddingGemma 2 的文字查询；(c) 先按标签筛选再用向量排序；(d) 用 RRF 或 z 分加分做融合。记录 R@10、MRR，并按语言分别统计。分级判断用 NDCG@10 计分，增益定为相关 2、部分相关 1、不相关 0；R@10、MRR 等二值指标把“部分相关”同时按相关与不相关各算一遍，两种口径都报告，避免一种口径单独决定比较结论。
2. **以图搜图。** 用 calibration 样本作查询图。“与它共享任一覆盖维度的 evaluation 样本”只作辅助指标：这本质上是标签重叠测试，天然偏向 PixAI 池化特征和 Dice 基线，例如两张只因同为 `hair:black` 就被记为相关的图。选定以图搜图的表示，要以独立的分级相关性判断为准，按构图、姿势、画风、氛围分别标注查询图与候选图的相关程度。比较 EmbeddingGemma 2 的图像向量、PixAI 池化特征（需要额外暴露输出），以及 Monbooru 式标签集合 Dice 系数基线（[anime-library-research](../anime-library-research.md)）。查询除整张图外，还要包括 roadmap 承诺的另两种起点：从样本裁出的局部（例如只含头部、手部或衣褶的参考视图，不同缩放比例）和库外截图（带绘画软件或网页界面像素、内容不在库中）；每种起点单独报告。计分与实验 1 相同：分级判断用 NDCG@10，增益 2／1／0，二值指标两种口径都报告。
3. **维数。** 只对 EmbeddingGemma 2 比较 768／512／256 维：它按 Matryoshka 训练，截短后重新归一化即可。PixAI 的 1024 维池化特征没有这种训练，直接截取前几维会改变相似度的含义，因此保持全维；如果确实需要降维，另行拟合降维方法（例如在库内样本上做 PCA）并单独评估。
4. **安全模式泄漏。** 把 r18 清单与 `sensitive` 样本一起放进库，开启安全模式后跑完实验 1 和 2 的全部查询。断言结果、计数与“较弱匹配”中都没有被封印的图；断言门槛与 z 分只按可见集合计算；断言设定返回 k 张时，确实拿到 k 张可见图（不因过滤而缩水）。再关闭安全模式，对 r18 清单与 `sensitive` 样本跑一组文字与以图查询，同样做分级相关性判断并按 NDCG@10 计分：模型训练数据经过过滤，对成人插画的表示可能很差，这部分不能只验证“隐藏”而不验证“找得到”。样本只有 14 张，结果只能作方向判断；若明显不可用，就在 roadmap 中把成人参考的语义搜索／以图搜图明确列为不支持，而不是默认可用。
5. **运行与数值。** 在验收机器（RX 6500 XT 4 GB）和一台无独显机器上，对 fp32、fp16、q8 各做一遍：按 DigUp 的门槛，与 CPU fp32 参考向量比较，最低余弦须 ≥ 0.999。这只证明执行提供方与量化前后一致；分词、图像预处理、张量接法或转换本身的错误会在 CPU fp32 上同样存在，照样能过门槛。因此先用 Google 官方参考路径（[sentence-transformers 示例](https://ai.google.dev/gemma/docs/embeddinggemma/inference-embeddinggemma-with-sentence-transformers)）为一组固定文字（含前缀）与图片生成金标向量，ONNX 的 CPU fp32 结果须先与金标对上，才以它为各精度的参考；检查 NaN；用 ORT 的 profiling 确认计算密集算子没有回落 CPU（形状计算等轻量节点按图分区规则留在 CPU 是正常的，与[验收约定](../../validation/acceptance.md)中 PixAI 的判定一致），只有回落导致主要计算移到 CPU 或超出响应预算时才判为不通过；记录每张图 p50／p95、峰值显存与内存、与 PixAI 同时加载还是先后加载、查询时文字编码的延迟。
6. **全量暴力查询。** “不需要 ANN”这一判断依赖暴力检索在目标规模上够快，必须单独测：用 20 万条合成向量（768 维 float16 与 PixAI 的 1024 维各一套），在两台验收机器上分别测冷启动（向量未在内存中，从 SQLite 读入）与热查询，完整走一遍“限定可见 id 集合 → 计算余弦 → 在集合内归一化与统计 → 对完整结果排序与折叠”，记录查询 p50／p95 与常驻内存。超出交互响应预算时，再考虑常驻内存矩阵、分块或 ANN。

**记录与判定：** 按[验收约定](../../validation/acceptance.md)的方式保存首版与修正版两份数字。是否保留某个方案，看“这一屏值得刷吗”的画师反馈和召回指标，而不是看模型榜单。
