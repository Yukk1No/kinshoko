# PROTOTYPE：Eagle 导入与参考组的备份恢复（#8）

用完可弃的验证原型，不是正式实现。对应 [#8](https://github.com/Yukk1No/kinshoko/issues/8)，门槛来自[验收约定](../../docs/validation/acceptance.md#导入与数据保护8)。

## 问题

[数据与存储模型提案](../../docs/discovery/data-storage-model.md)的候选格式是：每个资料库一个 SQLite，原文件按哈希命名存放；参考组是独立的带版本 JSON。用这套格式，能否在一组可核对的小样本里保全以下内容，并恢复出独立可用的库和组？

- 原图字节
- Eagle 整理信息
- 人工决定
- 跨库参考组

## 运行

```bash
python prototype/storage-roundtrip/run.py
```

只用 Python 3.11+ 标准库。每次运行先清空 `PROTOTYPE-wipe-me/`（已忽略），然后依次跑场景并逐项判定门槛，全部通过时退出码为 0。会生成两个文件：

- `PROTOTYPE-wipe-me/report.md`：门槛结果、字段保留清单、只记录的指标和场景记录。本目录的 [RESULTS.md](RESULTS.md) 是一次运行结果的副本。
- `PROTOTYPE-wipe-me/device2-恢复后/browse.html`：恢复出的库与参考组，图片内嵌，单文件可以直接发给画师确认。

`--images <目录>` 用真实图片字节代替生成的小图来构造批量库，例如 `samples/pixiv`。

## 画师电脑上的真实检查（`eagle_check.py`）

构造样本跑通以后，还要用 Eagle 真正写出的库再跑一遍，并请画师确认恢复结果（[#8](https://github.com/Yukk1No/kinshoko/issues/8)）。`eagle_check.py` 把这一步做成全自动：

1. **找库**：依次试 Eagle 本地 API（`localhost:41595/api/library/history`，Eagle 开着时可用）、`%APPDATA%\Eagle` 里设置文件记录的路径、扫描磁盘。有多个库时默认用最大的。
2. **挑样本**：按特征分层挑选，最多 300 张、1 GB。特征包括区域评论、多文件夹、链接、备注、回收站、PNG 与其他格式、极端比例、大文件、多标签和同库真实重复，挑完再随机补满。原库只读，样本复制到工作区。
3. **合成缺的形态**：两库共有原图；同库重复、Eagle 回收站和区域评论在样本里没有时才合成。“画师在 Eagle 里继续整理”由程序直接改副本模拟。合成了哪些都写进报告。
4. **跑门槛**：与 `run.py` 同一套，共 44 项。中断与部分失败用子进程注入故障；打包成 exe 后，子进程就是 exe 自己。
5. **画师确认**：打开 `browse.html`，图片引用工作区文件，不内嵌，区域评论画成框。控制台随后问 6 个问题：显示、区域评论坐标、局部、备份放哪、频率、其他。
6. **报告**：`kinshoko-eagle-check-报告-*.zip`，内含 `report.md` 和 `summary.json`。只有字段名、计数、耗时、容量和硬件型号，路径全部替换成占位符。

画师拿到的是 CI（`.github/workflows/eagle-check.yml`）打的 artifact：单个 exe 加 [使用说明.md](使用说明.md)。CI 用 `make_eagle_fixture.py` 生成一个仿真 Eagle 库和假的 `%APPDATA%\Eagle\Settings`，对 exe 自测，全部通过才上传。

开发时这样跑：

```bash
python make_eagle_fixture.py <临时目录>/fx --images samples/pixiv
APPDATA=<临时目录>/fx/appdata python prototype/storage-roundtrip/eagle_check.py --yes --no-open --work <临时目录>/w
```

**这一步修好的问题**：同样是 Windows 260 字符限制，参考组保存（临时文件＋替换）和组包解压也会超长，现在都走 `lp()`。浏览器按普通路径打开图片，所以 exe 放得太深时，工作区改到 `%LOCALAPPDATA%\kinshoko-check`。


| 文件 | 内容 |
|---|---|
| `kinshoko_store.py` | 候选实现：库表结构、Eagle／普通文件导入、人工决定、参考组、来源补足、备份范围、备份恢复、组包。值得保留的是表结构、身份规则和写入顺序 |
| `eagle_sample.py` | 按公开 Eagle 4.0 磁盘结构构造样本：主库、旧库、1000 项批量库，以及在 Eagle 里继续整理后的 v2 |

## 结论（2026-10-04）

42/42 项门槛通过，详见 [RESULTS.md](RESULTS.md)。

### 可用（构造样本上）

- **字段往返**：Eagle 单项 21 个字段，包括未知字段 `futureField`，和 6 个库级字段导入后都能取回。备份恢复后，每个库的全部表逐行一致（库身份除外），每张图的完整视图一致。参考组恢复后、以及从组包另存为新组后，裁切、位置、缩放和视口都逐字一致。
- **原文件 SHA-256**：导入、备份、恢复、组包四个环节都一致。库内原文件被外部改动时能检出：成员显示“内容不符”，不会静默显示新内容，备份也不会被标记为完整。
- **Q38 重试**：
  - 1000 项中有 12 项损坏（缺原图、坏 JSON、大小不符各 4 项）时，整体标为部分成功，保留 988 项，逐项给出原因；不修来源再试也不会重复创建记录，修好后补齐到 1000。
  - 三种中断都按预期处理：
    - 原文件发布后、记录提交前被杀：重试时复用已发布的文件。
    - 事务内被杀：整项回滚。
    - 参考组保存时被杀：旧版本完整。
    - 备份复制时被杀：半成品不会被当成完整备份，恢复会拒绝它。
- **Q43 备份范围**：默认范围包含全部库和组，连不引用任何库的组也在内。只选一个库时，A/B、B/C 关联链和 C/A 闭环都能一次算清并终止；不补选外库时列明未覆盖的组和库。
- **重导**：
  - 画师在本库做的否决、添加和备注都保留。
  - Eagle 里新增的标签和改过的备注会进来。
  - 来源换了内容 → 生成新图片记录并指向旧版本，旧裁切继续指向旧图。
  - 来源被删除 → 只标记缺失，本库副本保留。
  - 文件夹改名后，图片归属不变。
  - Eagle 库整体搬家后重导，先请用户确认是否同一来源，确认前不写任何数据；确认是同一来源就沿用登记，确认是另一个来源也不会重复创建记录。
- **同一原图**：同库两个 Eagle item 是同一原图时汇成一条记录，两份来源备注各自保留。两个库含相同原图时各自一条记录、各自整理。来源库离线时，用另一库字节相同的原图临时补足显示，不改写组文件。

### 已确认的规则（2026-10-04）

- **Eagle 回收站**：首次导入时，Eagle 回收站里的图进入本库的可恢复删除；之后 Eagle 再把图移入回收站，不改变本库状态。
- **来源搬家**：新位置与已登记来源的外部 ID 重合 ≥ 50% 时，只作为候选提出，由用户确认是同一来源（沿用登记、更新位置），还是另一个来源（新登记，相同原图汇入已有记录）。Eagle 没有稳定的库身份，不能自动认定。

### 需改进（试验暴露的缺口，需评审）

1. **Windows 路径长度**：备份内的 `libraries/<32 位库 ID>/originals/<2>/<64 位哈希>.<ext>` 加上仓库所在路径超过了 260 字符，首次运行在这里失败。原型改用 `\\?\` 长路径前缀后通过。正式规格需要二选一：全程支持长路径，或者缩短备份内的目录与文件名。
2. **普通文件导入必须记录尺寸**：最初只有 Eagle 导入带宽高，普通文件导入没带，局部裁切因此无法校验边界。现在导入时读取 PNG 尺寸，组校验也会拒绝缺少来源尺寸的裁切。正式实现要解码所有支持的格式，并处理 EXIF 方向。
3. **备注和 URL 的两份来源**：Eagle 的整图备注和 URL 留在来源快照里，随重导刷新；画师在本库写的备注单独存放（`note_manual`）。两者同时存在时界面怎么显示，还没有约定。 **已由访谈确定（alignment Q74～Q96，[PR #24](https://github.com/Yukk1No/kinshoko/pull/24)）。**
4. **文件夹的人工整理**：只给标签建了人工决定；画师在本库调整文件夹归属后，Eagle 重导会怎样，还没有建模。Eagle 里删掉的文件夹也没有测。 **已由访谈确定（alignment Q74～Q96，[PR #24](https://github.com/Yukk1No/kinshoko/pull/24)）。**
5. **新增的格式字段**：恢复出的组带 `restored_from`，从包另存的组带 `imported_from_package`，库内新增 `restore_provenance` 表。需要并入组格式和库格式的规格。
6. **备份一致性的前提**：原型依赖“原文件按哈希命名、写入后不改、没有清理”这一前提。永久删除或缓存清理上线后，备份期间要锁定所引用的文件。
7. **孤立原文件**：中断留下的未登记原文件会被报告、重试时复用，但还没有清理策略。 **已由访谈确定（alignment Q74～Q96，[PR #24](https://github.com/Yukk1No/kinshoko/pull/24)）。**

### 尚未验证

- **真实 Eagle 样本**：样本由脚本按公开结构构造，没有经过 Eagle 写出。正式样本要在画师电脑的 Eagle 里构造（一图多文件夹、标签、URL、备注、区域评论、两库共有原图）后，重跑同一套检查。
- **区域评论坐标**：基准与 EXIF 方向的对应只做了原样保留，标注为“未核验”。
- **真实规模**：用真实图片字节和画师规模的数据测导入、备份、恢复的耗时与容量。本次只记录了开发机上 1000 项小图的导入耗时，约 11 秒，每项都同步落盘。
- **Eagle 正在写入时导入**：读取期间 Eagle 改动库内文件的情况没有测。
- **范围外的操作**：库合并（A + B → C）与人工决定冲突、撤销删除与永久删除，不在本单范围内。
- **画师确认**：画师还没打开 `browse.html`，确认恢复后的素材与参考组都在。
